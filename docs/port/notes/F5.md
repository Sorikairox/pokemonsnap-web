# F5 — 2026-11-14: native-looking Options rows, Snap button hidden when Off, Motion Aim in the game's menu

Worked on `web` (from 3dadffe) and, for the host, in a retrowser worktree (`~/Code/retrowser-wt-motionopt`, branch
`motion-option` off retrowser main 665f135; not merged, not deployed). User report (iPhone landscape, retrowser.app):
"The Pokémonsnap custom menu are not well integrated. Changing the snap button also do not remove it from UI. Also
add the gyroscope control option in this option menu too." Design summary: `docs/port/FEATURES.md` ("The Options menu
with the port's rows", "Motion aim").

## 1. How the game draws its Options menu

Every row label ("• Screen"), every value ("< Stereo >", 56 x 10) and every description (238 x 30, one or two lines)
is a **picture** in the title scene's vpk0 data (`main_menu_vpk0`, decompressed to 0x802B5000 when the scene loads):
`G_IM_FMT_IA` 16-bit, intensity 255 everywhere, the letters in the alpha (anti-aliased), `SP_TEXSHUF` (the two 32-bit
words of each 64-bit word of the odd rows swapped), split in 32-pixel-wide bitmaps. Labels are drawn with the sprite
colour 0x80 / 0xFF (blink) / orange FF8241 (chosen), values orange (current) or 0x80/0xFF, descriptions 0xFF.

The face is **not** a font of the game: the window overlay's 8- and 12-pixel fonts (window/text.c, ROM 0x848BC0 /
0x84BA04) are different (smaller and lighter, resp. the larger face F1 used, with a 2-pixel drop shadow). The menu
pictures' text is the only source of that face. Letters present in the native menu text: A B C D H M N P R S Z,
a b c d e f g h i j k l m n o p r s t u v w y, "." ",", "<" ">" and the bullet; missing: E F G I J K L O Q T U V W X Y,
q x z, digits.

## 2. The port's rows composed from those letters (src/main_menu/A0D4D0.c, #ifdef PORT)

- `portGlyphs`: for each letter, which native picture, its first column and width, and the top of its text line (0 in
  labels / values, 3 and 15 in descriptions). Positions only: no pixel of the ROM is in the source. The table was made
  by segmenting each native picture into column runs and matching them with its known text (an offline scratch
  script; labels' first letter touches the bullet, so labels give only the bullet).
- `portNativeAlpha` reads a native picture's alpha at (x, y) through its Bitmap list (bands of `bmheight`, the
  TEXSHUF swap on odd rows). Runs in game code, so pointers and bytes are read the console way (vbe, K0 mapping).
- "O" = the native "C" with its left three columns mirrored; "x" is drawn in the code (6 rows, soft corners).
- Kerning (`portKern`): the next letter goes where its solid pixels (alpha >= 128) are at least 3 columns from the
  previous letter's on every row, with at least one empty column; a space adds 4. Fitted on the 15 native description
  lines: in-word positions differ from the native ones by +0.3 px on average, the native word gap is kern + 3.6.
- Label sprite 128 x 12: the native bullet ("Screen"'s columns 0-6) and the words from column 8. Value sprite 64 x 12:
  "< Mono >"'s brackets (columns 0-9 and 45-55) and the word centred on column 28 (the native values are centred
  there too). Description 256 x 30: lines at rows 3 and 15 from column 8, as the native ones. All IA16 (white + alpha),
  attributes `SP_TRANSPARENT` (no TEXSHUF: written unshuffled), widths powers of two (F1 trap), placed and coloured as
  F1 / F2 did (labels x 43, values x 163 / 222, ":" at x 158, y + 2 like the native rows).
- Texts, worded with the available letters (native style "X setting." for the row descriptions):
  Snap Button "Snap Button setting." / On "Hold Snap to focus, and release / Snap to take a picture." / Off "Snap
  Button does nothing. / Press Z and A to take pictures."; Pixels "Picture sharpness setting." / Smooth "Smooth,
  soft picture. / Photos and scores do not change." / Sharp "Sharp, crisp picture. / Photos ..."; Motion Aim
  "Motion Aim setting." / On "Aim by turning your phone, held / sideways. Allow it if asked." / Off "Aim with the
  Control Stick only."
- The 12-pixel font copy (`port_menu_font12`) is gone; `port_menu_alloc` has 32 slots (6 per row).
- Layout: rows 5 / 6 / 7 at y 137 / 153 / 169, Return 185, the description box 32 px down (y 198-231 of 240).

## 3. Snap button hidden when Off

Manifest `controls.extra` bit 16 gets `"when": 1`. The host (deployed and main) filters its touch buttons by the
options state (`touchExtra` in src/host/pages/player.tsx), which the `option-changed` message from
`rtw_option_changed` updates (`storeOption` -> `setOptions`): the button goes at once, no reload (e2e `options`:
"shown before true, after false", the Shutter stays).

## 4. Motion Aim as port option 3

`pc_options.c`: option 3, bool, default 0; `port_motion_add` drops motion while it is off (`[motion] dropped: option 3
(Motion Aim) is off`, once). Manifest: option 3 "Motion aim" `inGame`, `controls.motion: { "when": 3 }`.
`port/rtw/build.sh`: the shipped manifest is checked as written; if the check tool rejects `controls.motion`, the
object form falls back to `true` (then without the key). With an older host (motion: true) its ☰ Motion choice and
option 3 must both be on.

## 5. The host side (retrowser worktree `~/Code/retrowser-wt-motionopt`, branch `motion-option`; done by a helper agent)

- Manifest: `controls.motion` is `true` (unchanged) or `{ "when": <option id> }` (schema oneOf, validator regenerated;
  `validateManifest`, used by the host and `rtw-check`: an unknown id is an error, a non-`inGame` / non-bool option a
  warning). Spec §2 / §4.5 and guide.md updated.
- Value: `optionValue(m, id, values, locked)` (src/shared/manifest.ts; touchExtra uses it too): the lockstep-locked
  value, else the live / stored options, else the manifest default. `rtw_option_changed` updates it, so motion follows
  the game's menu at once.
- Tied: no ☰ Motion section, the stored ☰ choice ignored; motion is read while the option is not 0, the device can
  (motion API + touch) and the player did not refuse; landscape only and not while paused, as before.
- iOS permission: when the option turns on (or is on at start) the host calls `requestMotion()` at once without a
  gesture (Safari answers at once if it already allowed this origin); otherwise the banner `[data-state=motion-ask]`
  "Motion aim is on in the game's options: allow this page to read the motion sensors." with **Allow** (the tap calls
  `DeviceMotionEvent.requestPermission`) and **Not now** (only hides it; the game's option is never changed by the
  host). Denied: a message telling the player to turn Motion Aim off in the game's Options or allow Motion &
  Orientation Access in iOS Settings; motion stays off until the option goes off and on again. Remembered: the grant
  for the page's life (a ref); nothing stored across visits on purpose (the browser's own answer is the record, read
  by the silent try at start; a stored "allowed" could go stale and hide the prompt).
- Found on the way: a refusal reloaded the game's iframe (an empty-string `{motionMsg && ...}` text node let Preact
  move the `.screen` div) -> `!!motionMsg`; affects `motion: true` games too. This session added: banners take the
  theme's text colour (the prompt was light grey on white in the light scheme).
- The host validates every manifest when it opens a game (src/host/lib/game.ts -> validateManifest, the generated
  validator in the bundle). The deployed schema (retrowser.app/spec/retrowser.schema.json, = main) has `motion` as
  boolean only, so **the host must be deployed before rtw-dist ships `{ "when": 3 }`**; until then build.sh with the
  deployed tool ships `motion: true` (☰ Motion + option 3 both needed). `"when"` on extras is already deployed.
