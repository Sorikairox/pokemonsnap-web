## 1. Sharp pixels

**What is scaled**: only `vi_frame`'s final blit from the shown colour image's GL target onto the canvas. The colour
images the game draws and reads back (photo detection, scoring, the album) are untouched; the default (Smooth) path
is the old `glBlitFramebuffer(..., GL_LINEAR)` line, unchanged.

**Sharp = "sharp bilinear"**: n = ceil(fit scale); a `GL_NEAREST` blit of the 320x240 (or 640x480) image to n x into a
renderbuffer, then a `GL_LINEAR` blit down to the 4:3 fit; when the fit is exactly n x, a single nearest blit (the
harness's 640x480 canvas). Every N64 pixel becomes a same-size square; only edges blend, over at most one device
pixel. Chosen over:
- integer scaling + letterbox: portrait phone (390 css px at dpr 3, 1170 device px): 3x = 960 px, 18 % of the width
  lost on a picture that is already small; on 1440-tall desktops similar losses;
- plain nearest at the fit (3.66x): columns 3 and 4 device pixels wide in an irregular pattern: uneven letters, and
  the pattern crawls when the camera pans.
The retrowser host does the same for framebuffer games (loader.ts: integer pre-scale, smooth fit), so the two video
paths look alike.

**Canvas size** (`rtw_glue.js fit`): Smooth keeps S9's 4:3 canvas of the view x dpr (320x240 .. 1280x960). Sharp
uses the view x dpr itself (any shape, at most 4096 a side): the host shows the canvas with `object-fit: contain` in a
box of the view's shape, so it is shown 1:1 and the browser adds no resampling of its own (the 4:3 canvas rounded to
4 px, or clamped at 1280, would be rescaled by the page: a phone in landscape 844x390 at dpr 3 needs 1560 px).
`vi_frame` letterboxes. The glue reads `port_display_sharp()` before every retrace and resizes when it changes (the
menu's live preview included).

**Options row** "Pixels  < Smooth > < Sharp >" below "Snap Button" (row index 6, navigation 0 1 2 3 5 6 4 through a
table, `portRowStep`). F1's row code became a table of rows (`portOptRows`: option, which value is left, words,
descriptions); "Smooth" is 44 px in the 12-px font, so its brackets sit at 0 / 52 (Snap's 0 / 51), as tight as the
native "<Reverse>". Return moves to y 169 and the description box (frame lines, sides, all 13 description sprites)

## 2. The pacing check

Old check: `|R - 60| < 3 && wake-ups/s < 10`. The orchestrator's runs on one build: K (timer retraces per 600) = 28,
193 and 107 with 57.0, 56.6, 49.3 display frames/s: the wake-up count tracks how irregular headless Chrome's display
frames are, not a pacing fault. Accounting per 600-retrace window: retraces = started by a display frame + K, and
K = display deficit (60 - D per second) + display frames that came more than half a field late (the timer had
already run their retrace). The 193 case: deficit 33 + 160 late frames; every wake-up still ran a retrace.

New check (`pacingVerdict`): R = 60 +- 2; idle wake-ups (wake-ups - K) <= 3 + 2 % (rates are rounded in the line);
600 - K >= 60 % of the display frames (the display paces the game). The detail line prints the accounting. Applied to
the three orchestrator lines: all PASS (0 / 1 / 0 idle; 572 / 407 / 493 retraces started by 572 / 567 / 494 display
frames).

Mutants (copies of the built dist with the glue patched, re-hashed, `PHASES=desk`; never committed):
- idle chain (`arm` -> `setTimeout(onTimer, 1)`): **FAIL** "3481 wake-ups, 3338 idle (IDLE CHAIN)";
- timer-paced (display frames ignored, timer due at `next`): **FAIL** "0 retraces started by 576 display frames (NOT
  DISPLAY-PACED)".
Each mutant failed only this check (9 other desk checks passed).

  `--force-device-scale-factor=3`, which reaches the frame (canvas 1170x879). The `touch` phase keeps the old setup.
