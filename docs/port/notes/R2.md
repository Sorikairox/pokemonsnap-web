## 1. Blurry close-up textures (Valley rocks) -> 3-point filter

What the game asks for (before implementing anything):
- Static: every othermode macro in `assets/` and `src/` (matching build's extraction) is `SetTextureLOD(G_TL_TILE)`,
  `SetTextureDetail(G_TD_CLAMP)`, `SetTextureFilter(G_TF_BILERP)` (32 each); `G_TF_POINT` only in `26D80.c` and
  `window/8456E0.c` (sprites); no `G_TL_LOD`, `G_TD_DETAIL`/`SHARPEN`, `LOD_FRACTION`; every `gSPTexture` has level 0.
  Two-texture combiners use `PRIM_LOD_FRAC` (prim's LOD fraction, already a uniform), never `LOD_FRACTION`.
- Runtime: Valley retrace 7801 (`v_base`): all `G_TEXTURE` level 0, othermode H filter `0x2000` (BILERP), no LOD/detail
  bits. Probe at the left rock (N64 50,100 / 50,175): CI4 tile, mask 32x128 (tile 160x256, clamp bits), s 95..112 /
  t 53..205 across ~60 x 380 pixels: a ~3.5x magnification, so it is soft on the RDP too.

So mip-mapping / LOD / detail are not used by Snap; the only RDP behaviour the port did not reproduce for these
textures is the filter: GL's 4-texel bilinear vs the RDP's 3-point filter (N64 programming manual: the three texels
nearest the sample, T00/T10/T01 when fs + ft < 1, else T11/T01/T10). Implemented in the generated shader for
`G_TF_BILERP` in 1/2-cycle draws (`PF_3POINT`): three NEAREST fetches at texel centres, GL's wrap/mirror/clamp applied
per texel (as the tile's per-texel wrap/clamp). Texel centres stay where GL bilinear had them (s = 0.5 = texel 0's
centre, matching the model data's `st 0.5 .. 63.5`). Not emulated: the 5-bit filter fraction, `G_TF_AVERAGE` (unused).

Test `three_point_filter` (task 2): a 4x2 RGBA16 texture with white texels (0,0), (1,1) and black (1,0), (0,1),
magnified 16x with BILERP; pixel (15,15) gives red 2 of 31 (3-point: 1 - 2 x 0.46875); with the filter flag disabled
(mutant) it gives 16 (4-texel bilinear) and the check fails. Verified both ways.

Pictures: `v_cmp.png` (Valley 7801 before | after), `v_crop.png` (rock crop 3x): slightly more structure (diagonal
3-point shapes), still soft: that softness is the game's (small texture, large magnification). Beach
`beach_cmp.png` (8001 before | after): no visible regression.

Not changed: the VI blit scales the 320x240 image to the canvas with `GL_LINEAR` (on a phone this is ~3x) and adds
softness to everything, HUD included; the console's VI resamples horizontally and line-doubles. A "sharp pixels"
display option would be a presentation feature (an option, default off), not an RDP fix: left for the options work.

## 2. Cave floor seam near the end gate -> not a renderer bug

Cave retrace 11101 (`c_probe`, `c_probe2`; dense shots `c_seq_sheet.png` 10850..11350): the end scene's camera looks
at the gate; a straight horizontal edge crosses the whole screen at N64 y 142 (canvas 285) and hides the gate's base.
Probes (160,150), (160,144), (100,145): the floor triangles below the line end at vertices (109.6, 142.11, w 1238.3),
(210.4, 142.11, w 1238.3); probes (100,141), (250,141): the wall triangles above start at the same vertices plus
(44.0, 142.26, w 949.9) and (281.3, 142.25, w 959.8). Four rim vertices at depths 950..1238 project to one screen row:
the rim lies in a plane through the eye, i.e. the camera sits at the height of the ledge the floor ends at; the gate
stands lower behind it (its base vertex y 143.4 at w 1319). Depth and clipping are healthy: z/w 0.92..0.99, smallest
w 249 (near plane 10), nothing clipped, the far gate correctly hidden by the nearer floor. The renderer cannot make
four vertices coplanar with the eye. Not verifiable without a reference: whether the console's end-scene camera has
the same height (a game-logic difference in the camera path would show the same way; compare S10a's "Volcano camera
low over the ground" note). No change.

## 3. Credits 17: column of dots in the staff box -> not a renderer bug (memory layout)

Scene 17, retraces 450..452 (`sc17`, `sc17b`). The box is 8 texture rectangles 140x14 at x 90, y 68 + 14k (RGBA16,
`LoadBlock dxt 0` = pre-shuffled sprite, XLU `IN*A + MEM*(1-A)`); the dots are at row 0 of every strip, texels 0 and
2 (N64 x 90 and 92, y 82, 96, 110, ...). The loaded bytes of an empty box: `10A5 FC00 102B 6390 0000 0000 ...`, with
the 16 bytes before the source `10A5DD40 00000F60 00000001 00000000` = a UIMem `HeapChunk` header. Source:
credits/A937C0.c `func_credits_801DCD80` allocates the bitmaps with `UIMem_Allocate(14 * 140 * 2)`; the data starts
with the free-list link the allocator left there (`v.link.next`, `.prev`; window/83D730.c). Boxes whose photo is not
filled yet show those 8 bytes as 4 texels; the zeros after them are transparent (alpha bit 0). Texels 0 and 2 are the
pointers' high halves: in the port `0x10A5` / `0x102B` (wasm addresses: odd -> alpha bit 1 -> opaque bluish dots). On
the console the same words are `0x8025xxxx` (the chunk at the same RDRAM offset) and `0x803A6910` (the list head in
.bss): only texel 0 is opaque (`0x8025`: r 16, g 0, b 18 of 31, purple-ish) and texel 2 is transparent. So the console
most likely shows one dot per strip, in another colour; the port shows two. Root cause: game memory holds wasm
pointers where the console holds KSEG0 ones (MEMORY.md trap 2: behaviour depends on where things sit). Not fixable in
port/gfx; options for the orchestrator: leave it (cosmetic, credits only), or a narrow `#ifdef PORT` in the credits C
(e.g. write the console values / clear the 8 bytes after `UIMem_Allocate`) with a note that it is an approximation.

## 4. Tunnel purple / teal / yellow -> the game's own vertex colours

Tunnel retrace 6601 (`t_probe`), probes at the ceiling, wall and floor: geometry mode `00210405` (Z, SHADE, CULL_BACK,
FOG, SMOOTH; **no LIGHTING**), combiner TEXEL0 * SHADE, blender FOG * SHADE_A, fog colour 12515C. With lighting off the
shade is the vertex's RGBA as stored. The probed vertex colours (0.455 0.118 0.565, 0.094 0.286 0.384, 0.376 0.365
0.145, 0.608 0.180 0.408) are exactly (116,30,144), (24,73,98), (96,93,37), (155,46,104) / 255, all found in the
ROM's `assets/tunnel/block*/model.vtx.inc.c` (2424 vertices: 51 purple, 21 blue, 65 yellow by a simple hue count).
No change.
